# Experiment Design Builder — 实验方案生成与优化 Skill

## 1. 用途与适用范围

把研究目标落成能排期、能执行、能被同行评审的方案。四层递进：假设层（可检验）→ 变量层（可测量可操作）→ 执行层（绑定资源与参数）→ 处置层（失败预设）。

## 2. 输入识别（Step 0，必做）

1. 读 `/input/case.json`：output_contract 全部字段、case_id、研究目标、可用资源约束（设备/试剂/时间）、安全边界。
2. 约束登记：可用设备清单、试剂目录、时间预算——方案落在真实条件内。

## 3. 工作流程

### Step 1 假设与变量
- 目标 → 可检验假设（H1/H0，可判定真假）；概念 → 操作性变量：`{变量, 操作定义, 测量方法, 精度}`。

### Step 2 对照与判读
- 对照设计：阴性/阳性/基线对照（每个假设至少一个可比对照）；判读标准：`{预期结果模式 → 结论映射}`（什么结果支持/推翻假设）。

### Step 3 步骤绑定资源
- 每步骤：`{操作, 设备(型号), 试剂(规格/用量), 参数范围, 时间成本, 依赖步骤}`——可排期。
- 参数范围有依据（文献/SOP/仪器量程），依据标注。

### Step 4 失败与异常预设
- 预设失败模式：`{失败情形, 触发信号, 处置动作, 对结论的影响}`——实验做砸时知道下一步。

### Step 5 标注与评审
- 方案依据（文献/SOP）、假设（未经证实的前提）、**需专家确认项**（安全/关键参数）显式标注。

## 4. 输出契约

```json
{
  "case_id": "<原样>",
  "task": "experiment_design",
  "status": "success | partial | failed",
  "hypotheses": [{"id":"H1","statement":"可检验假设","testable_check":"判真/判假标准"}],
  "variables": [{"name":"温度","operational":"水浴锅实测，±0.5°C","measure":"数字温度计","role":"independent"}],
  "controls": [{"type":"negative","design":"不加酶对照","purpose":"排除自发降解"}],
  "readout": [{"pattern":"处理组显著高于对照组→支持H1","otherwise":"推翻或需复核"}],
  "steps": [{"n":1,"action":"...","equipment":"恒温水浴 X型","reagents":{"name":"酶液","spec":"...","amount":"5mL"},
             "param_range":"37±1°C（文献[2]）","time":"2h","depends":[]}],
  "failure_modes": [{"case":"反应产物低于检出限","signal":"OD<0.05","action":"提高底物浓度至2×重跑","impact":"时间+1天"}],
  "annotations": {"basis":["文献[2]"],"assumptions":["底物浓度与响应线性"],"expert_confirmation":["安全操作规程"]},
  "gaps": [], "uncertainty_notes": [], "changes": []
}
```

硬性要求：假设可检验、变量可操作；每假设有对照+判读标准；步骤绑定资源可排期；failure_modes 预设；专家确认项不省略。

## 5. 异常处理

| 情况 | 处置 |
|---|---|
| 资源约束无法满足设计 | 降级方案 + needs_human_review |
| 安全边界不明确 | 标 expert_confirmation，不冒险给参数 |
| 预算不足 | 假设+变量+对照层优先（partial） |

## 6. 自查清单

1. [ ] 假设可检验？变量可操作？
2. [ ] 对照+判读标准齐？
3. [ ] 步骤绑定设备/试剂/参数/时间？
4. [ ] 失败预设与处置具体？
5. [ ] result.json 含 output_contract 全部字段、case_id 原样？

## 7. 效率约束

预算 64 请求 / 900 秒。假设变量层先行；步骤表模板化填充；处置预设批处理。

## 附：运行时硬性契约（评分相关，逐条执行，优先级最高）

1. **Step 0 必做——读 output_contract**：打开 `/input/case.json`，找到 `output_contract` 字段。它定义 result.json 必须包含的全部字段。**原样保留字段名与嵌套结构，逐字段落实**；contract 缺失时按本文件 §4 结构输出并在 uncertainty_notes 登记。
2. **case_id**：从 `/input/case.json` 原样读取，禁止自造。
3. **事实依据**：数据/配置/日志/文献是事实依据；不编造数据、运行结果、软件状态。
4. **路径**：过程写 `/app/work/`；最终产物写 `/app/output/`（数据/图/代码文件 + result.json）。
5. **尽早落盘**：先写最小可用 result.json 再增强；中断时已落盘内容诚实合法（status=partial）。
6. **可追溯**：保留原始值、规则、结果、图表/代码和质量检查；每条结论带来源定位。
7. **交付物自检**：SKILL.md + README.md 一致，不一致以本节契约为准。

## v4 量化对账强化（基于 64 题出分复盘，11-22）

复盘规律：**评测分 ≈ 可量化对账产物密度 × 真实执行痕迹**。高分题（76-81）全部交付"每行可查的 CSV 对账表 + 状态枚举 + 计数断言"；低分题（39-59）败在"描述性框架无产物"。

本轮硬性要求（除本文件已有契约外追加）：

1. **数值型交付物**：按下方"本题针对性补强"列出的 CSV/脚本，全部真实生成到 /app/output/（不虚构行数与计数）。
2. **对账断言**：每张表给出计数对账（总数=分项之和），写进 result.json 的对账字段。
3. **真实执行**：任何统计/计数由脚本产出，run_log.md 逐条记录命令与输出摘要。
4. **契约不变**：result.json 逐字段落实 case.json 的 output_contract；case_id 原样；status 诚实 partial。

**本题针对性补强**：
1. 保持 74.7 分水准：steps.csv（设备/试剂/参数/时间/依赖）逐条
2. failure_modes 计数
