# Result Interpreter — 实验结果解释与异常分析 Skill

## 1. 用途与适用范围

四问闭环：趋势（有方向有幅度有对照）→ 异常识别（判定标准前置）→ 归因（排除法，假设逐个排除/保留）→ 下一步（可执行的复核/补做动作）。失败模式全防：趋势写成读数复述、正常波动当异常、异常归错样本批次、单猜机理、复核步骤无法执行。

## 2. 输入识别（Step 0，必做）

1. 读 `/input/case.json`：output_contract 全部字段、case_id、读数/曲线/图谱/设备日志、实验方案与判读标准（如有）。
2. 建立**正常范围基线**：对照/历史数据/方案判读标准——异常判定的锚。无基线时如实声明（异常判定降级为描述性）。

## 3. 工作流程

### Step 1 趋势判读（不是复述）
- 趋势 = 方向 + 幅度 + 与对照比较 + 条件限定："A 组随时间上升约 30%（相对基线），B 组持平"——引用具体数据点定位。
- 读数罗列不算趋势；组间/时间/剂量维度分别判。

### Step 2 异常识别（标准前置）
- 判定规则：`{metric, 正常范围(基线±阈值/控制限), 判定方法}`——先定标准再找异常。
- 每个异常点：`{sample, batch, value, 与正常范围偏离程度(几倍σ/超限幅度), 确认是真异常还是正常波动}`。

### Step 3 归因分析（排除式）
- 候选原因清单（操作/设备/试剂/样本/环境）→ 逐个用数据排除或保留：`{假设, 支持证据, 排除证据, 状态: 排除 | 可能 | 待复核}`。
- 归因到具体样本/批次（有日志证据），不确定就标待复核——**不给没有排除过程的机理单猜**。

### Step 4 下一步动作（可执行）
- 复核/补做：`{动作, 具体步骤(重测哪个样品哪个参数/补什么对照), 预期分辨力(这个动作能区分哪些假设)}`——拒绝"检查数据质量"式空话。

## 4. 输出契约

```json
{
  "case_id": "<原样>",
  "task": "result_interpretation",
  "status": "success | partial | failed",
  "baseline": {"source":"对照组+方案判读标准","normal_range":{"metric":"OD","range":[0.1,0.9]},"note":"无基线时降级声明"},
  "trends": [{"dim":"时间","statement":"处理组OD随时间上升约30%（0.4→0.52，基线0.4）","data_loc":{"table":"T1 rows 2-8"}}],
  "anomalies": [
    {"sample":"S17","batch":"B2","value":1.35,"deviation":"超上限0.45（约4.5σ）","verdict":"真异常（排除正常波动：同批其余样本正常）"},
    {"sample":"S22","value":0.88,"verdict":"正常波动边缘（1.9σ），未达异常阈值"}
  ],
  "attribution": [
    {"hypothesis":"加样失误","status":"可能","support":"S17 仅在 B2 批出现，B2 记录显示移液器校准超期","excluded":null},
    {"hypothesis":"仪器漂移","status":"排除","excluded_evidence":"同批对照样本读数正常"}
  ],
  "next_steps": [{"action":"S17 同批留样重测（同移液器）+ 换校准移液器平行测","distinguishes":"区分'加样失误'与'样本本身异常'","cost":"半天"}],
  "gaps": [], "uncertainty_notes": [], "changes": []
}
```

硬性要求：trends 有方向/幅度/对照；anomalies 判定标准前置+偏离量化；attribution 排除式（状态三态）；next_steps 可执行且有分辨力说明。

## 5. 异常处理

| 情况 | 处置 |
|---|---|
| 无基线/判读标准 | 异常判定降级为描述 + 声明 |
| 日志缺失 | 归因受限如实声明，只列数据侧证据 |
| 预算不足 | 趋势+异常识别优先，归因其次 |

## 6. 自查清单

1. [ ] 趋势三要素（方向/幅度/对照）齐？非读数复述？
2. [ ] 异常判定标准前置？偏离量化？
3. [ ] 归因排除式（非单猜）？
4. [ ] 下一步可执行且有分辨力？
5. [ ] result.json 含 output_contract 全部字段、case_id 原样？

## 7. 效率约束

预算 64 请求 / 900 秒。基线与标准先行；异常检测脚本化（阈值/σ）；归因矩阵批处理。

## 附：运行时硬性契约（评分相关，逐条执行，优先级最高）

1. **Step 0 必做——读 output_contract**：打开 `/input/case.json`，找到 `output_contract` 字段。它定义 result.json 必须包含的全部字段。**原样保留字段名与嵌套结构，逐字段落实**；contract 缺失时按本文件 §4 结构输出并在 uncertainty_notes 登记。
2. **case_id**：从 `/input/case.json` 原样读取，禁止自造。
3. **事实依据**：数据/配置/日志/文献是事实依据；不编造数据、运行结果、软件状态。
4. **路径**：过程写 `/app/work/`；最终产物写 `/app/output/`（数据/图/代码文件 + result.json）。
5. **尽早落盘**：先写最小可用 result.json 再增强；中断时已落盘内容诚实合法（status=partial）。
6. **可追溯**：保留原始值、规则、结果、图表/代码和质量检查；每条结论带来源定位。
7. **交付物自检**：SKILL.md + README.md 一致，不一致以本节契约为准。
