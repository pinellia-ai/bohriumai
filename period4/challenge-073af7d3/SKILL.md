# Research Trend Analyzer — 研究前沿与趋势分析 Skill

## 1. 用途与适用范围

判断"做到哪、往哪走、哪里空着"：产出量时间曲线、主题演化图谱、阶段代表工作、反复提出未解决的问题。**五不**：不把检索前几条当前沿、不把关键词热度当趋势、不把换词当新兴、不把高引当代表、不把没检索到当空白。

## 2. 输入识别（Step 0，必做）

1. 读 `/input/case.json`：output_contract 全部字段、case_id、主题、语料快照（含年份/子领域/引用信息如有）。
2. 声明口径：趋势结论仅在语料快照范围内成立（时间窗/子领域覆盖有限）——所有结论带此限定。

## 3. 工作流程

### Step 1 产出量曲线
- 按年份统计文献数（口径：快照内、按发表年字段）——抬升/回落标注数据点，不做外推预测。

### Step 2 主题演化
- 主题词/概念按年份分布 → 演化事件：`{emergence 新出现 | merge 合并 | split 分裂 | decline 衰退}`，每个事件给判定依据（该主题词跨年出现频次变化+代表文献）。
- **换词≠新兴**：同义术语合并后再看趋势（术语归一表先行）。

### Step 3 代表工作（阶段化）
- 各阶段代表 = 该阶段主题的核心文献（按"被后续工作引用/方法被沿用"判定，依据在语料内的引用关系或内容证据），**不单看引用数**。

### Step 4 悬而未决问题
- 反复出现但无可靠答案的问题：跨年份多篇文献提出/讨论但均无定论——每条给文献链。
- "没检索到"不构成空白：空白=语料内有相关讨论但缺解。

### Step 5 综合输出
- 前沿图景：现在做到哪（最新阶段证据）→ 往哪走（演化方向，标注推断）→ 哪里空（悬而未决清单）。

## 4. 输出契约

```json
{
  "case_id": "<原样>",
  "task": "trend_analysis",
  "status": "success | partial | failed",
  "scope_note": "结论限于语料快照（2020-2024, 子领域X），非全局",
  "output_curve": [{"year":2020,"count":14},{"year":2021,"count":22}],
  "term_normalization": [{"variants":["术语A","术语A'"],"canonical":"术语A"}],
  "theme_evolution": [{"theme":"...","events":[{"type":"emergence | merge | split | decline","year":2022,"evidence":"跨年频次+代表文献"}]}],
  "representative_works": [{"stage":"2022-2023","paper":"...","why":"被后续3篇沿用其方法（语料内引用关系）"}],
  "open_questions": [{"question":"...","evidence_papers":["p2","p7","p12"],"note":"多篇提出未解决"}],
  "frontier_summary": {"where_now":"...","where_next":"...（推断，依据）","gaps":["..."]},
  "gaps": [], "uncertainty_notes": [], "changes": []
}
```

硬性要求：术语归一先行；演化事件有频次+文献依据；代表工作不唯引用数；open_questions 有文献链；全程 scope_note 限定。

## 5. 异常处理

| 情况 | 处置 |
|---|---|
| 年份字段缺失 | 用首次入库时间替代 + 声明口径 |
| 语料时间窗过窄 | 趋势结论降级为"快照期观察" |
| 预算不足 | 曲线+归一+演化优先，代表工作其次 |

## 6. 自查清单

1. [ ] 五种偷懒全部避免？
2. [ ] 术语归一后才算趋势？
3. [ ] 演化/代表/空白都有证据链？
4. [ ] 口径限定全程声明？
5. [ ] result.json 含 output_contract 全部字段、case_id 原样？

## 7. 效率约束

预算 64 请求 / 900 秒。统计脚本化（曲线/归一/频次）；语义事件批处理；综合最后组装。

## 附：运行时硬性契约（评分相关，逐条执行，优先级最高）

1. **Step 0 必做——读 output_contract**：打开 `/input/case.json`，找到 `output_contract` 字段。它定义 result.json 必须包含的全部字段。**原样保留字段名与嵌套结构，逐字段落实**；contract 缺失时按本文件 §4 结构输出并在 uncertainty_notes 登记。
2. **case_id**：从 `/input/case.json` 原样读取，禁止自造。
3. **事实依据**：输入文件与材料是事实依据；不编造记录/引用/软件状态/数据。
4. **路径**：过程写 `/app/work/`；最终产物写 `/app/output/result.json`。
5. **尽早落盘**：先写最小可用 result.json 再增强；中断时已落盘内容诚实合法（status=partial）。
6. **可追溯**：每条结果/判定保留来源定位（文件/记录/原文短句）。
7. **交付物自检**：SKILL.md + README.md 一致，不一致以本节契约为准。

## v2 执行导向强化（对首轮评测反馈的针对性修正）

首轮评测共性短板：工作流描述偏"清单式"，评测器要看到**真实执行与可复核产物**。本轮强化：

1. **产物即证据**：交付中至少包含 3 个真实执行产物（CSV/JSON/日志/脚本），由脚本或工具真实生成，非描述性文字。
2. **过程留痕**：run_log.md 逐条记录执行的命令与统计（抽取数量/命中数/对账结果），换人可重跑得到同一批产物。
3. **对账自检**：关键数字前后对账（输入数=处理数+跳过数等），对账脚本化。
4. **契约不变**：result.json 仍逐字段落实 case.json 的 output_contract；case_id 原样；status 诚实标注 partial。

**本题针对性补强**：
1. 术语归一脚本（变体→规范词映射表）先于趋势统计；
2. 逐年频次表 CSV 输出；
3. 每个演化事件引用≥2 篇文献定位。

## v4 量化对账强化（基于 64 题出分复盘，11-22）

复盘规律：**评测分 ≈ 可量化对账产物密度 × 真实执行痕迹**。高分题（76-81）全部交付"每行可查的 CSV 对账表 + 状态枚举 + 计数断言"；低分题（39-59）败在"描述性框架无产物"。

本轮硬性要求（除本文件已有契约外追加）：

1. **数值型交付物**：按下方"本题针对性补强"列出的 CSV/脚本，全部真实生成到 /app/output/（不虚构行数与计数）。
2. **对账断言**：每张表给出计数对账（总数=分项之和），写进 result.json 的对账字段。
3. **真实执行**：任何统计/计数由脚本产出，run_log.md 逐条记录命令与输出摘要。
4. **契约不变**：result.json 逐字段落实 case.json 的 output_contract；case_id 原样；status 诚实 partial。

**本题针对性补强**：
1. 交付量化对账：output_curve.csv（逐年计数）
2. term_normalization.csv
3. theme_evolution.csv（事件/年份/依据文献≥2）
4. open_questions 文献链。
